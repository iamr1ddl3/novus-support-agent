A support agent that picks a tool, answers, or hands off to a human

Built with LangGraph. For each customer message it classifies the intent, calls the right tool (policy knowledge base, application tracker, account lookup), decides whether a human should take over, and replies. The customer's personal data is masked before any model sees it.

How it fits with the RAG assistant

The agent doesn't keep its own copy of the bank's policies. Its policy_kb tool calls the Novus RAG assistant's /query API in Hybrid mode and uses the passages it returns (design decision ADR-8). If the RAG API is unreachable, it falls back to a small in-memory retriever, so the agent still answers. That's why the RAG app is deployed first and torn down last.

Safety limit: MAX_STEPS = 6. If a query ever reaches 6 steps, evaluate sends it straight to respond, so the graph can't loop forever.

Which tool does it pick?

The classifier (gpt-4o-mini, temperature 0) labels the intent. Most intents map straight to a tool with a lookup table; one ambiguous intent gets a second LLM call. Click an intent.

The three tools

policy_kb: calls the RAG assistant's /query (Hybrid) for policy passages. Falls back to local retrieval if the API is down.

order_tracker: account-activation and loan-disbursement status. A realistic mock in this demo; production would call an order system.

account_lookup: tier details (Standard / Plus / Elite): interest, minimum balance, ATM limits, loan rates. Also a mock of the core banking system.

multi_tool: policy_kb first, then account_lookup, then answers from both.

When does it hand off to a human?

Escalation is a two-stage check in the evaluate step. Stage 1 is a free keyword scan. Only if a keyword matches does stage 2 ask gpt-4o-mini to confirm, which cuts false alarms. Type a message to run stage 1 live with the agent's real keyword list.

Keyword false positives are why stage 2 exists. "Is UPI urgent transfer free?" matches "urgent", but the LLM should say it's an ordinary question. If the LLM call fails, the agent trusts the keyword hit and escalates (fails safe).

Input guardrail

Blocks off-topic (e.g. IPL scores), prompt injection, staff impersonation and requests for internal policy before any tool runs. Blocked queries return a refusal with intent = "blocked".

What Langfuse sees

The trace input and output are the anonymized question and answer. LLM generations record model, output and token counts but not the prompt, because the guardrail's own call sees the raw question.

Known over-blocking (open): the guardrail refuses the UI's own "Escalation" and "Fraud" example chips, any message containing a phone number or PAN (so PII redaction is hard to demo live), and "What are the IMPS charges for a Plus customer?". The Standard-tier minimum balance answer is also wrong (₹10,000 instead of ₹1,000).

How well it works

42-query golden set: 32 answerable + 10 should-escalate. Faithfulness and correctness are LLM-judge scores normalized to 0–1. CI fails a PR if any metric drops more than 5 points.

Classification is the weakest number (75%), but routing still reaches 96.9% because several intents map to the same tool, so a wrong label often picks the right tool anyway.
LLM-judge noise is real: on 2026-11-22 a PR with no code change failed once with faithfulness −5.01 points (limit 5.00) and passed on re-run.

One query = one trace in Langfuse

Added on 2026-11-22 (scripts/tracing.py, Langfuse SDK v5 over OpenTelemetry). Click a span. This tree is the real shape of a policy question's trace.

Each trace is tagged with the intent (plus escalated or blocked) and carries metadata (tool, tools_called, steps_taken, escalation, pii_redacted), so in Langfuse you can filter for "all escalations" or "all multi-tool queries". Project: novus-support-agent, US region.

How it runs on AWS

CloudFormation stack acmera-support-dev in ap-south-1. No database: it reaches policy data through the RAG assistant's load balancer.
